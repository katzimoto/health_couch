# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal server that pulls Garmin Connect data daily into SQLite, exposes it to ChatGPT Pro via an MCP connector, and runs a two-way Telegram coach (OpenAI-backed) that pushes a 07:30 morning plan and answers questions grounded in the user's own data. One Docker image, several containers each running a different command (see `docker-compose.yml`).

## Commands

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

python -m pytest                    # offline tests (DB + analysis), no network needed
python -m pytest tests/test_data.py::test_analyzer_report_and_flags   # single test

docker compose up -d scheduler mcp tunnel   # Phase 1: data + ChatGPT connector
docker compose up -d telegram               # Phase 2/3: enable the Telegram coach
docker compose logs -f <service>            # scheduler | mcp | tunnel | telegram
docker compose run --rm scheduler python scripts/garmin_login.py   # cache Garmin tokens (once, or after ~6mo expiry)
docker compose run --rm scheduler python scripts/backfill.py 180   # backfill N days on demand
docker compose run --rm telegram python scripts/get_chat_id.py     # find your Telegram chat id
docker compose run --rm scheduler python scripts/import_apple_health.py /app/data/export.zip  # import an Apple Health export (idempotent; --since YYYY-MM-DD to limit)
```

There is no lint/typecheck config in this repo — `pytest` is the only checked command.

## Architecture

**One image, several roles.** `Dockerfile` builds a single image; `docker-compose.yml` runs it as four services that differ only in their `command`: `scheduler` (APScheduler: hourly Garmin sync of today, daily pull + gap healing, 07:30 plan push, minutely Telegram-reminder dispatch, nightly backup), `mcp` (FastMCP HTTP server for ChatGPT), `tunnel` (Cloudflare Tunnel, exposes `mcp` publicly), `telegram` (long-polling bot). All services share `./data` (SQLite) and `./garmin-tokens` (Garmin auth) as mounted volumes.

**Data flow:** `garmin_client.py` (`GarminClient`) pulls per-metric data from Garmin Connect into SQLModel tables in `database.py`/`models.py`, keyed by `day` (ISO string). Upserts are field-preserving (`Database._upsert`): non-`None` incoming fields update the row, existing values are never blanked — re-pulls are idempotent and a partial write (e.g. `log_weight` with only `weight_kg`) can't erase fields a fuller write stored. Successful pulls are recorded per-day in `pull_log`, which the scheduler's nightly gap healing (`GarminClient.pull_missing_days`) uses to recover from interrupted backfills. `analysis.py` (`Analyzer`) reads a hand-written `daily_summary` SQL view (joins all metric tables, recreated on every DB init in `database.py`) and computes 7d-vs-28d trends, sleep debt, acute:chronic training-load ratio, and plain-language flags. `coach.py` (`Coach`) feeds that analyzer report (never raw DB rows) into an OpenAI system prompt to produce either a structured morning plan or a free-text chat reply, with conversation history persisted in the `Conversation` table for multi-turn memory. Both `mcp_server.py` and `telegram_bot.py` are thin consumers of `Coach`/`Analyzer`/`Database`.

**Telegram reminders:** `reminders.py` owns recurrence math (`compute_next_run`, pure and unit-tested) and CRUD over `telegram_reminder`/`telegram_reminder_delivery` (soft delete; exact-duplicate creates dedupe). Each reminder stores its next fire time in UTC (`next_run_at`); the scheduler polls due rows once a minute and delivers via `telegram_sender.py` (direct Bot-API HTTP, no PTB Application). Failure policy: within `Reminders.SEND_GRACE` a failed send keeps `next_run_at` so the next poll retries; past it the firing is recorded as `missed` and the schedule advances — never a backlog flood after downtime. User replies (`/meal`, `/water`, `/skipped lunch`, `/done workout`) land as structured rows in `health_event`, which ChatGPT reads via `get_health_events` and the evening report (`Coach.evening_report`) consumes.

**The daily coaching context is the flagship read.** `coaching_context.py` assembles one structured payload answering "based on all my current data, what should I do today?" — exposed as the `get_today_coaching_context` MCP tool (alias `generate_daily_plan`) and consumed by the 07:30 morning-plan job via `Coach._data_context`. Its two decision functions are deliberately **pure** (no DB/clock/network) so coaching logic is unit-testable: `classify_recovery` weighs sleep *against the user's configured target* (never a hard-coded 8h) plus HRV/resting-HR/stress/Body-Battery/load into `{status, confidence, reasons}` (`good|moderate|low|compromised` — a short night reduces, it never cancels; pain/illness escalates), and `build_recommendation` maps that status to a structured decision (training decision/intensity, suggested session, step/cardio/sleep/hydration targets, nutrition priorities, one top priority). `build_coaching_context(db, refresh_if_stale=, garmin_sync=)` takes an *injected* sync callback so a stale Garmin pull refreshes before reading yet the read still degrades to cached data with a visible `data_freshness` warning if Garmin is unreachable — and so the scheduler reuses the exact interactive read path with no connector round-trip. `data_freshness.sources` reports which sources were retrieved vs missing. See `docs/DAILY_COACHING_UPGRADE.md`.

**Sleep need is configurable, effective-dated, and never a hard-coded 8h.** The baseline is 7.0h. `Profile.sleep_*` fields hold the current target/band/floor; `sleep_target_history` stores effective-dated changes so historical sleep-debt stays reproducible (`Database.sleep_target_for(day)` resolves per-night). `Analyzer.sleep_debt` is the shortfall vs the configured target, clamped `max(0, target - actual)` per night, surfaced as an **estimate**. Set it via `set_sleep_target` (proper effective date) or `set_profile`. Hydration targets are likewise persistent (`Profile.hydration_*`, `Database.hydration_targets()`, defaults 2750/3250/3250 ml) — and **missing hydration is reported as unknown, never zero**.

**Nutrition carries provenance.** `Meal` has `sodium_mg`, `source`, `source_record_id`, `is_estimated` (all nullable); a calories-only meal is valid and totals only sum present values. `add_meal` dedupes idempotently on `(source, source_record_id)`. The Apple Health importer imports dietary sodium and tags its rows `source="apple"`.

**Config is centralized:** every module reads `garmin_coach.config.settings` (a frozen dataclass populated once from `.env`/env vars) rather than touching `os.environ` directly.

**Strength numbers are never trusted as typed:** SQLModel `table=True` models skip validation and SQLite is dynamically typed, so strength rows can hold `"3"`, `"12.5"`, a rep range `"10-12"`, or a JSON list where the schema means a number. All sets/reps/weight/RPE arithmetic — `Database.exercise_history`, `_prepare_exercise`'s aggregate derivation, `progression.recommend_next_weight` — goes through `exercise_metrics.py` (`parse_float`/`parse_int`/`parse_rep_range`/`parse_reps`, `normalize_performance`): unusable values normalize to `None` with a structured warning (endpoint/exercise/session/row/field/raw), never a guessed number or a crash, and history rows carry a `data_quality` note that gates recommendations (no `increase` off uninterpretable data). Rep ranges are bounds for progression thresholds only — never multiplied as a rep count. Don't add new calculations over these columns without routing them through this module.

**Training-day automation:** `create_workout_reminder_pack` (`workout_reminders.py` has the pure time math) generates a linked set of one-off Telegram reminders around a `TrainingPlan`'s workout time — pre-workout meal, hydration, gym start, post-workout meal, workout log — tagged and metadata'd with `plan_id`/`reminder_type` so re-running resyncs (rather than duplicates) the same reminders after the plan changes. `update_training_plan` (`Database.update_training_plan`) is the generic partial-update path every plan-mutating tool now goes through; every changed field is diffed into a `training_plan_edit` audit row and `TrainingPlan.updated_at` is bumped. `merge_garmin_strength_fragments` (`strength_merge.py` has the pure grouping heuristic) folds same-day Garmin strength fragments into one canonical `Workout` row (`source="garmin_merged"`) and points the originals at it via `duplicate_of` — the same soft-delete field `dedupe_workouts` uses — so summaries/training load/workout counts see the session once while the raw Garmin rows are kept. `merge_workout_sources` (`workout_merge.py` has the pure matcher + field-priority resolver) does *field-level* merging across sources: a manual strength log and a same-day Garmin activity of the one session are linked into a canonical `Workout` row (`source="merged"`) whose `field_sources` JSON records, per field, which source won — **manual for exercise details, Garmin for physiology/load** (`exercise_details`: manual>apple>garmin; `physiology`/`duration`/`calories`: garmin>apple>manual; `training_load`: garmin>manual-estimated>apple-estimated; name/type: manual for strength, Garmin for cardio). Both source rows are preserved and marked `duplicate_of` the canonical (never hard-deleted), each recorded in a `workout_source_link` row (`match_confidence`/`match_reason`/`fields_imported`), and `strength_session.activity_id` is repointed to the canonical so exercise edits (`update_strength_session`) re-derive the canonical without clobbering Garmin physiology. This is distinct from `merge_garmin_strength_fragments` (which folds several *Garmin* rows into one Garmin session); `dedupe_workouts` runs field-level merge first, then the classic row-level marking for the rest. Reverse a bad match with `unmerge_workout_sources`; `backfill_workout_source_merges` is an opt-in, idempotent historical pass. `get_nutrition_gaps` (`nutrition_gaps.py`) never infers a meal was skipped from silence — only an explicit `skipped_meal` health event counts — and only flags a meal category "missing" once its local-time window has started. The Telegram guided workout-completion flow (`workout_flow.py`'s `advance`, a pure function over a state dict, wrapped by `WorkoutLogFlows` for the `workout_log_flow` table) is intercepted ahead of every other handler in `telegram_bot.py` (`route_active_flow`, registered in handler group `-1` with `ApplicationHandlerStop`) so `/cancel`/`/skip`/`/done` and free text are routed into an open flow instead of their normal command meaning.

**Progression analytics share one aggregation contract.** `activity_progress.py` owns windowing, calendar-week bucketing (user timezone, partial weeks marked), activity-type alias normalization (synonyms fold; pool/open-water, indoor/outdoor and treadmill/road stay distinct), weighted aggregation and trend slopes — sport specialists reuse those primitives so their totals can't disagree with the generic `get_activity_progress(type, days)` view. Aggregate pace is always total distance ÷ total time (never the mean of per-session paces), a zero/absent baseline yields `percent_change: None`, unsupported metrics return `null` plus an `*_unavailable_reason`, and days without a recorded sync are *unknown*, never rest. See `docs/PROGRESSION_ANALYTICS.md`.

**Swim detail is ingested separately from the daily summary.** Garmin's per-day activity list has one duration and no lengths, so `garmin_client._pull_activity_detail` makes a second per-activity call for swim types into `activity_detail` (separate elapsed/timer/active clocks, rest + its derivation, pool length only when the unit is known, stroke) and `activity_length` (per-length rows, `is_rest` marked). It is wrapped per activity so a detail failure never costs the day's summary; every attempt is recorded (`ok|empty|unsupported|error`) so `pull_activity_details` is a bounded, resumable backfill that never re-asks the same questions; lengths are *replaced* on re-sync, never appended. `swimming.py` is pure over those rows: elapsed and active pace are separate series, rest only comes from a documented compatible pair, and a continuous 50/100/200/400 m best is the fastest *contiguous* run of non-rest lengths summing to the distance exactly — never interpolated, never bridged across a rest.

**Strength progression is per-set-exact and convention-aware.** `strength_progress.py` reads `Database.exercise_history` (already normalized by `exercise_metrics`) and adds the longitudinal half: completed volume is Σ(reps × weight) over the *recorded sets* — a top-weight aggregate is never multiplied by all reps, and an aggregate-only row is labelled `volume_basis: "aggregate_estimate"`; `top_set_weight_kg` vs `working_weight_kg` distinguishes a heavier single from moving every working set up; estimated 1RM (Epley) is produced only from a completed 1–10-rep set and always flagged an estimate; alias folding is conservative (equipment, machine and variant words never fold) and `load_convention` states per-hand / total / machine-stack / bodyweight / assisted / unknown rather than assuming. Skipped or substituted work never inflates volume, and unreadable rows are excluded from records with the exclusion reported.

**Workout reconciliation is quality-aware, and there is exactly one warning pipeline.** `workout_quality.py` produces typed findings (near-zero duration, partial recording, zero distance, impossible speed, missing essentials, source mismatch, unresolved match candidate) with evidence and a suggested action; `coaching_context.detect_workout_quality_warnings` is now a legacy-shaped wrapper over it, so extend that module rather than adding a detector. `source_quality` marks a source incomplete when its duration covers <50% of the longest recording of the same session, and `merge_fields(..., quality=...)` then demotes it for the *whole-session* domains (duration/calories/training_load) whatever the usual priority says — its HR is still kept, annotated `covers: "partial"` via `coverage_annotations` into the canonical's `meta_json` and surfaced by `get_merged_workout.field_coverage`. Same-date alone never merges: an unresolved candidate is reported, not resolved. `get_workout_data_quality` is read-only by construction, and `record_blocking_ids` is what keeps unusable recordings out of progression records and totals.

**Training load is decomposable by sport without changing the metric.** `sport_load.py` buckets the same `Workout.training_load` column with the same normalizer `activity_progress` uses, so the sport buckets sum to the reported total (`reconciliation.reconciles`) and a single-sport history gets the same acute:chronic ratio as `Analyzer.acute_chronic_ratio` (same EWMA spans, same first-recorded-day seeding). `load_by_source` keeps device EPOC load, the documented estimate and manual entries distinct; a sport with <21 days of its own history or zero chronic load returns an unavailable ratio with a reason; strength's supplemental workload (working sets, kg × reps) is a separate, non-additive block that survives a device recording no HR or load; and `rest_and_coverage` separates confirmed rest from days that never synced. `get_training_load(days, by_sport=True)` keeps the legacy shape and adds the breakdown.

**Failure isolation is a deliberate pattern**, not an oversight — preserve it when touching these paths:
- `garmin_client.py`: every per-metric pull (`_pull_sleep`, `_pull_hrv`, etc.) is wrapped individually in `pull_day`, so one broken Garmin endpoint doesn't abort the rest of the day's pull. The `_get` helper walks nested dict/list keys defensively since Garmin's undocumented JSON shape varies by device/firmware.
- `scheduler.py`: Garmin login failure at boot, backfill failure, and each scheduled job are all caught and logged individually so the container stays up and jobs retry on their own schedule. The morning-plan job additionally retries with backoff (reusing the already-saved plan, not regenerating), and the nightly pull heals a bounded number of missing history days per run.
- `telegram_bot.py` and `scheduler.py` run blocking work (OpenAI calls, Garmin pulls) via `asyncio.to_thread` so the event loop — polling, other handlers, scheduled jobs — never stalls behind it. Long-running services touch `data/heartbeats/<service>` (see `heartbeat.py`); the compose healthchecks check that file's freshness, so keep the beats alive when restructuring these loops.

**Security boundaries to preserve:**
- Only the analyzer's *summaries* are sent to the OpenAI API — never raw DB rows (see `coach.py` docstring).
- `mcp_server.py` requires OAuth via WorkOS AuthKit (`AUTHKIT_DOMAIN` + `MCP_PUBLIC_URL`) for any deployment reachable publicly — needed for ChatGPT's connector, which requires OAuth rather than a static token. AuthKit is wired as a resource-server-only integration (`AuthKitProvider`): WorkOS runs the actual authorization server (login, consent, PKCE, token issuance) via a hosted AuthKit domain with sign-up disabled and exactly one invited user, and this process only verifies the JWTs WorkOS issues — no custom OAuth server code lives here. Falls back to a static `MCP_BEARER_TOKEN` if AuthKit isn't configured; logs a loud warning (not an error) if neither is set.
- `telegram_bot.py` restricts all handlers to `TELEGRAM_CHAT_ID` via `_authorized()` so a leaked bot handle can't leak health data or spend API credits.
- `.env`, `data/`, and `garmin-tokens/` are git-ignored; don't add code paths that would write secrets into the repo or the SQLite file's tracked contents.

## Adding a new Garmin metric

Touches four places in order: add a table to `models.py`, add it to the `daily_summary` view + an `upsert_*` method in `database.py`, add a `_pull_*` extractor wired into the `pulls` dict in `garmin_client.py`, and if it should be queryable by column name, add it to `SUMMARY_COLUMNS` in `models.py`.

## Schema changes and migrations

`create_all` never alters existing tables, so live databases need explicit evolution — both layers run automatically on every startup (`Database.init_schema`):
- **New nullable column on an existing table:** just add it to the model. The generic reconciler (`Database._migrate_missing_columns`) adds it via `ALTER TABLE … ADD COLUMN`, backfilled as `NULL`.
- **Anything else** (data backfills, indexes, NOT NULL columns, renames): an Alembic revision. The environment lives *inside the package* (`garmin_coach/alembic/` — deliberately, so the Docker image ships it; `alembic.ini` at the root is only for the CLI). Create one with `alembic revision -m "..."` (or `--autogenerate`), put the real logic in `garmin_coach/migrations.py` as a plain-`Connection` function the revision script calls — that keeps it unit-testable — and write it guarded/idempotent (table/column-existence checks), because startup order is `create_all` → column reconciler → `upgrade head`, so on fresh databases the tables already exist in final shape and revisions must no-op cleanly (and may rely on reconciled columns existing). Startup upgrades run under a cross-container file lock (`data/.migrations.lock`) since all four services boot against one SQLite file.
- New *tables* need nothing: `create_all` handles them.

Every deploy also snapshots the DB first (`data/backups/pre-deploy-*.db`, newest 7 kept — see `.github/workflows/deploy.yml`), so any migration can be rolled back to the exact pre-deploy state.
